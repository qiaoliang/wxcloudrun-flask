
## 测试用例的分析维度

- 功能维度：核心业务逻辑是否闭环、输入输出是否符合预期、业务规则是否被满足；
- 边界维度：入参的极值、空值、异常格式，数据量的上限 / 下限，场景的临界条件（如 “订单金额 = 0”“用户注册时手机号格式正确但已被占用”）；
- 异常维度：网络异常、数据库连接失败、依赖服务不可用、权限不足等异常场景的处理逻辑；
- 兼容维度（若涉及多环境 / 多版本）：不同操作系统、不同浏览器、不同接口版本的兼容性要求；
- 性能维度（可选）：高并发场景、大数据量查询的响应时间要求。

## 测试用例的输出格式

- 以Markdown表格形式输出测试分析结果，表格列包括：分析维度、测试要点、对应代码片段、备注；
- 按“核心功能→边界条件→异常场景”的层级，用分级列表输出分析结果，每个要点标注优先级（高/中/低）。

## 编写高质量测试场景


- 以 “用户视角 / 业务流程” 为核心，避免技术导向
- 采用 “全覆盖 + 重点突出” 的策略，避免遗漏核心场景
- 按优先级（高/中/低）对测试场景进行分类，高优先级场景需详细描述操作流程，中/低优先级场景简要描述核心要点。
- 遵循 “一个用例覆盖一个最小可验证的功能点 / 边界条件 / 异常场景” 的原则

### 测试场景的描述格式与规范

测试场景的描述需具备 “场景名称、前置条件、操作步骤、预期结果” 四个核心要素

示例格式参考
```markdown
场景名称：正常支付（微信）；
前置条件：用户已登录、购物车有商品、提交订单成功、账户余额充足；
操作步骤：
	- 1. 进入订单详情页；
	- 2. 选择微信支付；
	- 3. 完成支付操作；
预期结果：支付成功、订单状态更新为“已支付”、扣除对应账户金额。
```

## 精准分解测试用例（粒度适中且可执行）

测试用例是测试场景的细化，是 “可直接执行的最小测试单元”，核心是**粒度适中、步骤清晰、预期明确、可重复执行**.

1. 遵循 “一个场景对应多个用例” 的原则，进行精细化拆解
2. 测试用例需包含完整核心要素，确保可执行性
3. 聚焦 “可重复性” 和 “无歧义性”，避免模糊表述
```
  反例：“点击相关按钮”
  正例：“点击订单详情页右下角的‘立即支付’按钮”
```
